## Distilled Learnings

### 1) Configuration Controls Scope, Framework Controls Semantics
- Search/index scope should be explicitly configured by field inclusion per type.
- Operator behavior should remain deterministic and framework-defined from `TypeInfo` and field shape, not redefined by consumers.
- Routing principle: indexed path when field+operator is supported, otherwise scan+compare fallback to preserve correctness.

### 2) Field-Aware Query Routing Is the Core Reliability Pattern
- Multi-field fulltext support is most maintainable when query routing is criteria-driven and field-targeted.
- `list`-style APIs should infer fulltext routing from criteria/operators instead of taking ad hoc fulltext arguments.
- Unsupported or negated fulltext semantics (`NOT_LIKE`, `NOT_CONTAINS`, suffix-negation cases) should explicitly fall back until complement-set/suffix index strategies exist.

### 3) Centralize Path Semantics in Shared Routing Utilities
- Relative route resolution (`/`, ``, `./`, `../`, `../../`) must be canonicalized in shared routing utilities and reused across app/web/native adapters.
- Adapter wrappers should normalize `push`/`replace` behavior so default `Route` usage works without extra consumer setup.

### 4) Accuracy First, Cost Reduction Second
- Production indexing changes should be introduced with an explicit type/operator matrix and parity expectations.
- Structured indexing fanout can be reduced significantly through field inclusion gating and tokenizer selection, while maintaining supported-query correctness via fallback paths.
- For this cycle, `1-3gram` was retained as the safe default for correctness; narrower grams reduced fanout further but increased behavior risk.

### 5) Verification and Consumer Clarity Are Part of Feature Completion
- Feature completion in this repo includes: implementation, JSON spec coverage, doc comments, integration docs, examples, and demo usage updates.
- Observability hooks for write/routing behavior materially improve confidence when changing indexing strategies.
- Keep documentation explicit about operator routing, fallback behavior, and limitations to avoid stale or inferred contracts.

## Reusable Standards for Future Work
- Define contract first: config schema, precedence, and routing rules.
- Encode operator/field behavior in tests close to implementation.
- Prefer deterministic fallback over partial indexed support when correctness is uncertain.
- Treat docs/examples/demo as required deliverables for behavior changes, not optional follow-up.
